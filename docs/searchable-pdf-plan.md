# 里程碑：扫描件 → 可搜索 PDF（写出侧）

## 为什么是这个，而不是直接从"清除坏文字层"开始

调研把两件事指为最大的行业空白：**清除/替换已有坏文字层**（OCRmyPDF 维护者称
"single most-requested capability"）与**选区粒度**（"一划一大片"，≥14 issue / 5 项目）。

但这两件事**都落在同一个东西上，而那个东西在本项目里还不存在**：可搜索 PDF 的写出侧。

现状盘点：

| 环节 | 状态 |
|---|---|
| 识别（PP-OCR） | ✅ 97.5% char F1，20 份真实英文论文 |
| 阅读顺序 | ✅ better 8 / worse 0 / +13.2% |
| **每个块的框坐标** | ✅ 已经在手（这正是写出文字层所需的一切）|
| **写出可搜索 PDF** | ❌ **未开始** |

所以写出侧是唯一缺环，而且它一旦存在，"清除坏文字层"就不是一个额外功能，而是
**默认行为**（我们总是重新生成文字层，而不是往旧层上叠）。

## 验收标准（先定死，再动手）

写出来的 PDF 必须同时满足这五条，缺一条都算没做完：

1. **可选中** —— 在 macOS Preview 与 Acrobat 里都能选中文字并复制。
2. **文本一致** —— `pdftotext` 抽回的文本与 OCR 文本（按我们的阅读顺序）**≥99% 相同**。
3. **逐词框对齐** —— 每个词的隐藏文字框与 OCR 框的偏差，**中位数 < 2% 页宽**。
   这一条专门防"一划一大片"：粗到块级的框会让选区永远糊成一片。
4. **不叠加文字层** —— 输入已带文字层时，结果是**替换**。验证方式：`pdftotext` 只应抽到
   一遍文本，不是两遍。（`paperless-ngx#13263` 正是"重复文字层"这种病害。）
5. **视觉零改变** —— 页面像素级等同于原图。隐藏文字用渲染模式 3（`3 Tr`），
   不落任何可见像素。

## 许可证红线（会决定能选哪个库）

产品闭源商用，所以写出库必须允许：

- ✅ 可用：`lopdf`（MIT）、`qpdf`（Apache-2.0）
- ❌ **禁用：PyMuPDF / fitz（AGPL）** —— 它是最顺手的 PDF 库，因此也是最容易误踩的那个

## 第一步

用 Rust + `lopdf` 做最小闭环：**一张 PNG + PP-OCR 的词框 → 可搜索 PDF**。
然后写 `check_text_layer.py`（与 `compare_orders.py` 同类）**自动跑上面五条** ——
不靠肉眼，因为肉眼看不出第 3 条和第 5 条的细微违反。

## 顺序

1. 最小写出侧 + 五条自动检查（本里程碑）
2. 阅读顺序接进写出侧（已就绪，直接消费）
3. 多栏 + 通栏定位（补阅读顺序的已知缺口）
4. 真实纸张扫描件复测（一旦有真实语料）

## 写法参考：pdf-textlayer（PyPI，2026-05）核实记录

做同样工作的现成项目（OCR JSON → 隐形可搜索层），值得抄它的做法与注意事项。

**它确认的标准做法**（补上了本项目缺的那一步）：

- 逐词用**自己的 bbox**，坐标原点在左上、y 向下，单位是 PDF user-space points
- **把字号缩放成"渲染出的文本宽度 = 框宽"** —— 不是用 Tz，而是缩放字号
- 插入点放在**字形基线**，即 (x, y + height)，也就是框的底部
- 用 **render mode 3** 写（与我们的做法一致）

→ 对本项目的意义：我们的逐词位置应该**先按真实字宽比例分配行框宽度**，再**把每个词的字号缩放到"渲染宽度 = 分配宽度"**。这样几何与图一致，**漂移与合并会同时消失**——它们是同一个根因的两个表现。

**许可证陷阱**：`pdf-textlayer` 自己是 MIT，但**依赖 PyMuPDF（AGPL）**，正在我们的禁列上。
→ 不能作为依赖，但**技术可以照抄**（我们已经在用 lopdf）。

**它也踩过、于是我们可以提前避开的坑**：

| 它的限制 | 对我们的意义 |
|---|---|
| 文档自述 **"No de-duplication across overlay and native text"**，靠 `fontName` 过滤规避 | 我们的验收第 4 条要求**替换而非叠加**，正是同一类问题。**它没解决、我们要解决** —— 而这恰好是调研里 `OCRmyPDF#1696` 所称"最被请求、至今没有干净答案"的能力 |
| 旋转文本被**正立绘制** | 我们也会遇到（扫描件常见轻微旋转） |
| 默认 helv 字体只覆盖 Latin-1，不支持字符变 `?` | 与我们实测一致（该 PDF 页只有 3 个非 ASCII 字符） |

**一个值得注意的差异**：它只**叠加**（并跳过原生文本页），我们要**替换**。范围上我们更难，但那是用户真正在要的东西。
