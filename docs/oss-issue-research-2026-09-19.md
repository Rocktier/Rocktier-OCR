# 竞品 issue 调研（2026-09-19）

方法：`gh issue list/view/search` 按仓库做主题检索 + 高评论数排序 + 精读约 25 条正文。
覆盖：tesseract、OCRmyPDF、PaddleOCR、EasyOCR、docTR、surya、tesseract.js、paperless-ngx、
scribe.js、Umi-OCR，另加两个免费竞品 NAPS2、gImageReader。

**调研者自陈的局限**（读结论前先看）：GitHub Search API 限流，PaddleOCR 与 tesseract.js 只取了
头部列表未做深度检索；未覆盖 Reddit / HN / 应用商店评论 —— 所以"价格 / 隐私"两节本就薄弱。

## 一、最重要的一个结论：我们正在做的正是行业公认缺口

**多栏阅读顺序是跨项目、跨引擎、长期未解决的短板，且维护者自己承认受限于底层分割算法。**

证据（6 个项目、≥15 个 issue）：`surya#245/#367/#561/#150`、`doctr#2084/#1586/#1795`、
`EasyOCR#414`、`OCRmyPDF#1091/#813/#642/#1518`、`tesseract#4072/#4389/#4426`、`Umi-OCR#165`。

最有力的一条是 **`OCRmyPDF#1696`**（官方 roadmap 汇总）里维护者的原话：把
"Better handling of separated/columnar text for copy-paste order" 归为长期诉求，并注明
**"largely a Tesseract segmentation limitation"**。

也就是说：`reading_order.py` 不是在补一个小瑕疵，而是在攻这一行的公认缺口。

## 二、机会清单（按对我们定位的性价比）

| # | 机会 | 证据强度 |
|---|---|---|
| 1 | **多栏阅读顺序 + 按正确顺序写入文字层**（我们在做） | 极强：6 项目 ≥15 issue，含维护者自认 |
| 2 | **文字层逐词对齐与选区粒度**（划选一划一大片） | 极强：≥14 issue / 5 项目；Umi-OCR 两个引擎都错位 |
| 3 | **输出体积控制 / DPI 降采样**（我们已有降采样方案） | 极强：`OCRmyPDF#541` **102 评论＝全仓库第一**；`#1698`（降采样 DPI 选项）**至今是空 issue** |
| 4 | **清除/替换已有坏文字层，且不栅格化整页** | 强：≥10 issue；维护者称其为 **"single most-requested capability"** |
| 5 | **零依赖安装 + 小体积 + macOS/Apple Silicon 原生** | 强：≥30 issue；macOS 尤其空白 —— Umi-OCR **完全没有 mac 版**（6 个 issue 在问），NAPS2 mac 端长期坏（7 个） |
| 6 | macOS Preview/Safari/Quartz 渲染兼容（产出的 PDF 必须能在系统查看器里正常） | 中：4–5 issue，成本低、体验敏感 |
| 7 | 批量 + 选页范围 + 保留原文件名 + 双页拆分 | 中：6–8 issue |
| 8 | 轻量纠错（只改错字、重跑单页） | 中：≥8 issue，但成本高，建议 v2 |

反向情报（`OCRmyPDF#1237`）：有用户拿 macOS 自带 LiveText 处理 Tesseract 搞不定的 PDF，但
**LiveText 遇到已带文字层的 PDF 不会激活**，且 macOS 14 起找不到免费 GUI 把 PDF 打平成纯图片。
→ macOS 自带 OCR 有单点优势，但**不能批量、不能处理已有文字层、不输出可搜索 PDF**：正是空隙。

## 三、不要做（有人要，但破坏边界或定位）

1. **表格结构抽取 / 输出 Markdown / Excel / Word** —— `tesseract#1714`（70 评论、17👍）等要得最凶，但这是数据抽取，正面踩我们划死的边界。
2. **接入云端 OCR / LLM / VLM** —— `OCRmyPDF#595/#1186/#1434/#1093`、`tesseract#3754`；上游一律拒绝，反证"纯本地"是这类工具的价值锚点。
3. **做文档管理系统**（paperless-ngx 那种：标签、全文检索、Docker、邮件摄取）—— 另一个产品、另一套运维。
4. **做人工校对编辑器 / hOCR 编辑器** —— `gImageReader#438` 要了 8 年仍 open；喊得响、用得少、开发量大，会把我们变成"编辑器"。只留第 8 项那种最小形态。
5. **输出"纯文本无图 PDF"** —— `OCRmyPDF#537` 被拒；丢掉原图就没人能发现识别错误。
6. **RTL／中日韩／竖排／多语言优先** —— 需求大但不是我们的用户，会稀释英文准确率投入。**架构别堵死，产品不投入。**
7. **页面数会变化的操作**（删空白页、拆双页、裁剪、合并不同来源）—— `OCRmyPDF#1696` 明确说这类因对无人值守批处理风险太大被搁置。我们只做单文件进、单文件出。

## 四、证据不足 —— 不要拿这些当依据

1. **价格敏感度与付费意愿：零 issue 证据。** GitHub 几乎不讨论价格；web 搜索只返回 SEO 软文。`$9.99–19.99` 的合理性，本调研**无法提供证据**。
2. **"离线/隐私是购买驱动"：证据很弱** —— 仅 `OCRmyPDF#1407`（2 评论）一条正面提及。间接佐证是官方拒绝云 OCR 的立场，但那是维护者立场，不等于用户调研。
3. **"macOS 用户愿为 OCR 付费"：纯推测。** 找到的是"没有 mac 版"的诉求（17 个 issue），没有一条能证明他们会掏钱。
4. **阅读顺序错误造成多大实际损失**：无量化证据。只看到抱怨，没看到"因此弃用"。
5. **用户画像偏差**：Umi-OCR / paperless-ngx 的中文与自托管用户占比高，其抱怨未必代表我们的目标用户。

## 五、一个值得记住的观察

调研者注意到：**中文引擎社区（PaddleOCR / Umi-OCR）关心"能不能跑起来"，英文工具社区关心"结果对不对"** ——
头部 issue 集中在训练、部署、内存 vs 阅读顺序、文字层坐标、选区。

这从另一个角度支持了英文优先的定位：**在英文工具社区，"结果正确性"本身就是可售卖的东西。**
